# Предметная область: универсальные правила и метки

Документ задаёт **целевую архитектуру** (как в enterprise-конфигураторах) и показывает, **как она отражена** в текущем прототипе без хардкода `if product.type == "controller"`.

## 1. Принцип: типы не ведут логику

В реальном каталоге устройства бывают **controller, switch, router, firewall, server, AP, gateway, …** и сотни vendor-специфичных классов. То же касается опций: **license, module, PSU, fan, cable, software, expansion_card, …**

**Важно:** ни класс устройства, ни «тип опции» **сами по себе** не должны включать ветвления вроде «если контроллер — только лицензии». Лицензии и модули могут быть у разных классов железа; поведение задаёт **набор правил и связей** (какие опции привязаны к какому продукту, какие фильтры и лимиты действуют).

В прототипе **нет** кода вида `if product_category == "controller": …` для валидации. Поле **`product_category`** — **только метка** (аналог части `attributes` в идеальной схеме).

## 2. Целевая модель (эталон)

| Сущность | Назначение |
|----------|------------|
| **Product** | Корень строки конфигурации: `id`, `name`, атрибуты (в т.ч. метка категории). |
| **Option** | Опция, привязанная к продукту: `id`, `name`, атрибуты (скорость, размер пакета, …). |
| **Rule** | Связь продукт ↔ опция / контекст: `rule_type`, `config` (JSON). |

Примеры **типов правил** (логика в `config`, а не в `if` по категории устройства):

| rule_type (идея) | Смысл | Пример config |
|------------------|--------|----------------|
| **FILTER** | Отбор опций по полю | `field: speed_gbps`, `allowed: [1, 10]` |
| **QUANTITY** | Лимиты количества | `min`, `max`, `step` |
| **CALCULATION** | Расчёт пакетов (лицензии) | `included`, набор размеров пакетов, целевой `target_ap` |
| **COMPATIBILITY** | Несовместимости | пары id, запреты сочетаний |

Админ настраивает **доступные опции, фильтры, расчёты и ограничения**, а не «выбрал тип устройства — получил захардкоженное поведение».

## 3. Отображение на текущий код (нормализованно)

Полноценная одна таблица `rules` с JSON в этом репозитории **не введена** (объём диплома / миграций); вместо этого правила **разнесены по полям и таблицам**, но **принцип тот же**: поведение следует из данных и сервисов, а не из категории `controller`/`switch`.

| Идея Rule | Где в проекте |
|-----------|----------------|
| FILTER по скорости модулей | `products.module_speeds_json` **или** первое правило `rules_json`: `{"type":"filter","field":"speed","allowed":[…]}` (приоритет у JSON); реализация: `product_rules_runtime.effective_speed_allowlist` + `GET /products/{id}/configuration-options` |
| QUANTITY (модуль / слоты) | `modules.max_quantity`, `products.max_module_slots` **или** `rules_json`: `{"type":"limit","field":"modules","max":N}`; проверка в `validate_structured_lines` |
| CALCULATION (лицензии AP) | `products.built_in_license_units` **или** `rules_json`: `{"type":"license","included":N}`; строки `licenses.units_per_pack`, `suggest_license_packs` |
| COMPATIBILITY | `compatibility_rules`, `product_incompatible_pairs`; `compatibility_service` |
| Привязка опций к продукту | `modules.product_id`, `licenses.product_id` |
| Метка класса устройства (не для валидации) | `products.product_category` (строка, опционально) |
| Участие строки как корня в `lines[]` | `products.product_kind == "equipment"` — **не** «тип железа», а флаг роли в API конфигурации |

Имя **`equipment_product_id`** в API — историческое: это **id корневого продукта строки**, а не утверждение, что устройство физически «только коммутатор».

## 4. Слой правил в коде

Точка входа для разработчиков: `app.services.rule_engine` (реэкспорт валидации, подбора пакетов, совместимости, **эффективных** ограничений из `rules_json`).

Исполняемый разбор `rules_json`: `app.services.product_rules_runtime` (типы `filter` / `limit` / `license`). Парсинг колонки скоростей: `app.services.speed_allowlist.parse_speed_allowlist_json`.

- `config_validation.validate_structured_lines` — ограничения и принадлежность опций.
- `config_validation.suggest_license_packs` — подбор пакетов под цель AP.
- `compatibility_service` — запреты и пары (если заданы в БД).

## 5. Админка и пользовательский сценарий

- Каталог: продукт с **категорией-меткой** (`product_category`), полями правил (встроенные AP, JSON скоростей, лимит слотов).
- Опции: модули и лицензии в БД с `product_id` (сиды, SQLAdmin, API).
- Пользователь: выбор корня → опции с учётом фильтров и лимитов → сохранение с проверкой на сервере.

---

**Для защиты:** подчёркивать сдвиг мышления — **универсальные правила и связи**; **controller/switch** и **license/module** в продукте — **метки и специализации схемы**, а не ветки `if` в бизнес-логике. Текущая реализация — **шаг к** полной таблице `Rule(config)`, уже без привязки поведения к «типу устройства».
